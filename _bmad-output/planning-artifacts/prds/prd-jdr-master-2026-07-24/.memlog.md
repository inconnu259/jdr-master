- (decision) Processus : même pipeline BMad complet que les paliers précédents (PRD -> epics/stories -> sprint-status.yaml -> dev-story -> code-review par story), pas un mode allégé.
- (decision) Enjeux calibrés hobby/solo. Mode de travail : coaching path, point d'entrée Vision + Features (capability-first, cohérent avec les PRD précédents). Aucune source additionnelle à fournir — l'utilisateur dictera le contenu officiel du livre au fur et à mesure pendant le dev.
- (decision) Magie : scope complet dans ce palier (règles + listes de sorts), malgré l'absence totale de modèle existant au-delà du type Magie (+4 PE).
- (decision) Règles d'équipement : plusieurs listes du livre seront saisies avec description dans le contenu seedé, mais une seule sera réellement câblée/utilisée dans ce palier — le reste attend la future refonte UI (Palier 9).
- (decision) Occupations/actions par classe : texte de référence pur (pistes de jeu/idées de métier pour le joueur), aucune validation/mécanique de jeu dessus.
- (decision) Migration des personnages existants (refonte armes) : aucune migration réelle nécessaire, pas de mise en prod — seed-demo.ts sera simplement mis à jour/reset. Pattern à suivre : mettre à jour le seed de test, pas écrire de migration one-off comme l'Épic 14.
- (decision) Équipement de départ : nouvelle étape wizard remplace le mode pique-nique auto-assigné actuel (FIXED_EQUIPMENT, equipment-step.ts) — le joueur choisit entre (a) le nécessaire de voyage pré-fait (pique-nique, à compléter/enrichir) ou (b) un achat libre avec un budget de 1000 Po dans une liste figée en fichier (même pattern JSON-seedé que les autres catalogues).
- (decision) Refonte du choix d'arme : le joueur choisit une arme précise (ex. dague, arbalète), qui appartient à une grande catégorie (arc/épée courte/.../portant les formules touche+dégâts+encombrement). Catégorie enrichie d'une description + liste non-exhaustive d'armes types. Possibilité de créer une arme libre hors liste. Touche validate()/weapon-step/character-wizard.
- (decision) Rôles de groupe (cartographe/chef/chroniqueur/intendant, exactement 4, pas plus) : assignation manuelle par le MJ à un personnage de la Partie (pas de choix joueur, pas de vote — décidé). Affiché via un badge sur l'avatar du personnage, même emplacement que le badge de montée de niveau existant (RosterRow.hasPendingLevelUp, roster-row.util.ts) — le badge rôle est momentanément masqué quand une montée de niveau est en attente (priorité au badge level-up).
