# Architecture Spine Review — jdr-master Palier 3

## Overall verdict

Solid, well-reconciled spine — all 14 PRD FRs now map to a concrete route/AD, brownfield claims (no `CharacterService.update()`, `validate('mj')` no-op, `updatePortrait` optimistic-lock shape, no `GameSystemPlugin` interface, `equipment.individual: string[]`) all verified accurate against the actual repo, and no Deferred entry looks unsafe to leave undecided. Two real gaps remain: a dangling forward-reference ("AD-6bis") that leaves the email-trigger path for MJ-direct XP edits unspecified, and a genuine operational-envelope gap around ordering the AD-3 data migration relative to code deploy — the one area the checklist explicitly asked to be verified as a real gap, and it is.

## Findings

- **high** AD-6's note promises "Seule la notification e-mail (**AD-6bis** ci-dessous) nécessite un déclenchement serveur explicite" but no `AD-6bis` section exists anywhere in the document — it's a dangling forward-reference. The only place the `'level-up'` email send is actually shown is in the XP-distribution sequence diagram (`XDS->>ES: sendMail('level-up', ...)`), which covers only the distribution path. The MJ-direct-XP-edit path (`PATCH /characters/:id/xp`) can also cross a level threshold per FR-14's own conséquence #4 ("le système applique la même détection de montée de niveau qu'une distribution normale"), but nothing says whether that path also triggers the email, or from which service call. Two builders implementing the XP-edit endpoint vs. the distribution endpoint could genuinely diverge on whether/how the email fires. (location: AD-6, "Notification in-app" paragraph). *Fix:* either add the missing subsection (rename to a real AD or fold into AD-6's Rule) stating explicitly which service call triggers `sendMail('level-up', ...)` for the direct-XP-edit path, mirroring the distribution-path diagram.

- **high** No migration-rollout ordering for AD-3's inventory shape change (`equipment.individual: string[] → InventoryItem[]`). The spine says a "script one-off" converts existing rows, and separately that `pdf-field-map.ts` "doit lire `.name` au lieu de la valeur brute" — but never states the required order between (a) running the data-migration script and (b) deploying the new code that assumes the new shape. If the new `pdf-field-map.ts`/inventory-read code goes live before the one-off script finishes, existing Palier-2 characters (real data, confirmed to exist per `.memlog.md`) will have `.name` read off a raw string and either crash or silently render `undefined`. This is exactly the "operational/environmental envelope" dimension the checklist flagged as suspiciously silent, and it is a real, exploitable gap here — Prisma's own migration (`character_evolution_p3`) only handles the schema-level `Character.xp` column addition (safe, has `@default(0)`); it does *not* cover the JSON reshape, which needs a separately-sequenced imperative script. (location: AD-3, "Migration requise" paragraph). *Fix:* state explicitly that the data-migration script must complete before the new code is live (e.g., "run as part of the same deploy step, before app restart, blocking"), or alternatively require `pdf-field-map.ts`/any inventory-reading code to defensively accept both `string` and `InventoryItem` entries during a transition window.

- **medium** Inherited Invariants table row "`P2-AD-3` | `PartiesService` reste le seul point de vérité pour l'appartenance/rôle MJ (`getOwned`, `getViewable`)" does not match the actual AD-3 in the cited Palier 2 spine (`architecture-jdr-master-2026-06-27/ARCHITECTURE-SPINE.md`), whose AD-3 is "`GET /parties/:id/available-slots` dans `PartiesController`" (endpoint placement, not authority-over-membership). The statement being cited instead matches, semantically, **P1-AD-3** as listed inside that same Palier 2 spine's own Inherited Invariants table ("`PartiesModule` exporte `PartiesService` pour les modules qui vérifient l'appartenance ou le rôle MJ"). This mislabeling was not introduced by this spine — it was already present verbatim in the Palier 4 spine's Inherited Invariants table — but this spine propagates it a second time without correcting the traceability. (location: Inherited Invariants table, row `P2-AD-3`). *Fix:* relabel to `P1-AD-3` (or verify against the actual Palier 1 spine if available) so the citation traces to a real, matching AD.

- **low** AD-2's generic `capability: { type: CapabilityType; params: Record<string, unknown> }` shape effectively resolves PRD §8 Open Question 2 (storage format for repeated "Classe"/"Type" secondary capabilities — PRD explicitly leaves this open, to be "décidé en fonction de l'UI, à traiter en phase UX/architecture") but never says so. Nothing in DESIGN.md/EXPERIENCE.md calls this out as the resolution either. Low risk since the generic shape is compatible with any concrete UI, but a story-writer reading only the PRD's still-"open" §8 OQ2 could reasonably re-litigate the storage format. (location: AD-2). *Fix:* add one sentence noting this closes PRD §8 OQ2.

- **low** FR-2's calcul-assisté inputs (`difficulty`, `breaths`, `monsterLevel`) are captured on `CreateXpDistributionDto` alongside the (separately client-adjustable) `entries[].amount`, but the spine never states whether the server independently re-derives/validates the suggested total from those three inputs or purely stores them as audit metadata while trusting `entries[].amount` as authoritative. FR-2 does say the calc is "jamais bloquant," which implies the latter, but it's not spelled out at the AD level. (location: AD-6 shared-types block / `CreateXpDistributionDto`). *Fix:* one line: "server never recomputes `amount` from `difficulty`/`breaths`/`monsterLevel` — stored for audit/display only; `entries[].amount` is authoritative."

## What's solid

- All 14 FRs (FR-1..FR-14) now map to a concrete route and AD after the reconciliation pass — no silent gaps found this time.
- Brownfield claims cross-checked line-by-line against `character.service.ts` and `validate.ts` are all accurate: no generic `update()`, `validate('mj', ...)` is genuinely a no-op today, the `updatePortrait` optimistic-lock pattern (`updateMany({where:{id, updatedAt}})` → 409 on `count===0`) is exactly reused in AD-9, and `GameSystemPlugin` has zero matches in the codebase (confirmed via repo-wide search) — `GameSystemService.getSchema()`'s own comment corroborates "pas encore de registre de plugin par système."
- Every Deferred entry is genuinely safe to leave undecided for this palier — none creates an exploitable two-builder ambiguity (all are either single-implementer generality, explicit PRD non-goals, or pushed to a documented future palier).
- AD-1/AD-6's XP-vs-sheetData split is a deliberate, well-justified deviation from a literal reading of PRD FR-14 (which lists "XP" among the freely-editable `sheetData` fields) — the spine explicitly cites the PRD's own "high"-severity quality-review flag as justification, which is the right way to resolve a PRD/architecture tension rather than silently diverging.
