# Version/Currency Review — jdr-master Palier 3 Architecture Spine

## Overall verdict

The spine introduces **zero new external dependencies** — every decision (AD-1 through AD-10) reuses the existing NestJS/Angular/Prisma/PostgreSQL stack and existing in-repo conventions (`PrismaService`, `parties.getOwned`/`getViewable`, `EmailService.sendMail`, control-flow `@if/@for`). There is therefore no library-choice claim that needed web verification. The one claim that *did* need — and got — a reality check against the actual repo is the Prisma generator, and it holds up: `apps/api/prisma/schema.prisma` currently declares `generator client { provider = "prisma-client-js" }` (legacy generator, not yet migrated to the new `prisma-client` generator mentioned in CLAUDE.md as planned for a future palier). All Prisma schema syntax used in the spine's additions (`Json`, `enum`, `@@index`, `@default(uuid())`, `@updatedAt`, relation fields) was cross-checked against current Prisma 7 (7.6.0) documentation via Context7 and is valid and unchanged — this syntax is generator-agnostic model/field syntax, not something that shifts between `prisma-client-js` and `prisma-client`.

## Findings

- **low** The spine never states explicitly that it verified the live generator in `apps/api/prisma/schema.prisma` before writing Prisma blocks that assume legacy-generator-compatible syntax (which it happens to use correctly). AD-1/AD-5's Prisma blocks match today's `prisma-client-js` reality, but the spine doesn't cite this check, so a future reader can't tell if it was verified or merely assumed to still work. *Fix:* add a one-line note under AD-5 or the Prisma schema block, e.g. "confirmed against `apps/api/prisma/schema.prisma`'s current `generator client { provider = "prisma-client-js" }` — no generator migration in scope this palier," making the reality-check explicit and auditable.
- **low** AD-1's code comment `Character.xp Int @default(0)` and the full schema block are correct current Prisma syntax, but the spine doesn't flag that if/when the project's planned migration to the new `prisma-client` generator (CLAUDE.md: "prévue au palier 1") lands before or during Palier 3 implementation, the `output` path and generated import paths (`@prisma/client` vs custom `output`) used by any new service code (`XpDistributionsService`, `CharacterService.setXp`) would need to match whichever generator is live at implementation time — not a defect in the spine, but worth a one-line forward-pointer given the CLAUDE.md explicitly calls out this migration as pending. *Fix:* optionally add to Deferred: "Generator migration (`prisma-client-js` → `prisma-client`) — tracked separately at Palier 1, not this palier's concern; new models/fields here are generator-syntax-neutral."

No findings at medium/high/critical — nothing in the spine's TypeScript, Prisma, or endpoint syntax is stale, invalid, or non-idiomatic for a 2026-era NestJS/Angular codebase (interfaces, union types, and route signatures all match current idiomatic style, and no deprecated Prisma attribute or scalar type is used).
