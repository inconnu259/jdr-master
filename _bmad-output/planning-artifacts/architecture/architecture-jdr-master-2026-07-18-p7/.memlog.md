- (constraint) Auth = session cookie (express-session + connect-pg-simple + Passport), CORS déjà configuré credentials:true sur WEB_ORIGIN (main.ts:19-50). EventSource enverra le cookie de session automatiquement en prod (same-origin derrière Cloudflare Tunnel) ; en dev (ng serve cross-origin), le client doit passer withCredentials:true.
- (constraint) Signal 'changed' existant = signal Angular writable simple (signal(0), .update(v=>v+1)), lu via effect()+untracked() pour déclencher un refetch (ScenariosService, pattern répété dans scenario-timeline.ts/partie-detail.ts/character-sheet.ts/homme-dragon-sheet.ts). C'est LE pattern à étendre, pas une RxJS Subject.
- (constraint) Aucun module NestJS de type events/pub-sub n'existe (pas de @nestjs/event-emitter, pas de @nestjs/websockets dans apps/api/package.json). Modules existants : auth, availability, characters, common, email, game-systems, health, homme-dragon, invitations, notifications, parties, poll, prisma, scenarios, users, xp-distributions — injection croisée via exports/imports Nest standard, pas de module core partagé.
- (constraint) Aucune config de reverse proxy committée (pas de nginx/Caddy dans le repo) ; déploiement cible = Raspberry Pi + Cloudflare Tunnel (docs/spec.md), timeouts/keepalive pour connexions longues SSE pas encore adressés — terrain vierge.
- (constraint) Confirmé : SSE/WebSocket/EventSource/polling totalement absents du codebase actuel (apps/api et apps/web) — mécanisme 100% greenfield, aucun conflit à réconcilier avec un existant.
- (decision) Bus d'événements serveur : service partagé PartieEventsService (RxJS Subject/Observable fait main), pas de nouvelle dépendance @nestjs/event-emitter. Binds : tout module émettant un changement scopé Partie. Prevents : coexistence de deux mécanismes de notification différents (bus nommé + Subject ad hoc) sur un besoin qui ne comporte qu'un seul type d'événement.
- (decision) Déclenchement de l'émission : appel explicite this.partieEvents.emit(partieId) en fin de chaque méthode de mutation concernée, pas d'intercepteur automatique. Binds : toutes les méthodes de mutation à travers scenarios/poll/characters/invitations/announcements. Prevents : un mélange où certaines mutations notifient via intercepteur et d'autres manuellement — un seul chemin, cohérent avec FR-15 du PRD (checklist humaine, pas de garde automatisée).
- (decision) Câblage frontend : un service partagé (PartieRealtimeService) possède la connexion EventSource par Partie et, à réception d'un événement, appelle une méthode publique notifyChanged() sur chaque service de domaine concerné (ScenariosService, CharacterService, etc.) — pas un signal partagé unique auquel chaque composant s'abonnerait en plus du sien. Binds : tout service de domaine possédant un signal _changed privé. Prevents : deux mécanismes de refetch parallèles (signal local vs signal partagé) à maintenir en synchro dans les mêmes composants.
- (decision) Encapsulation frontend : les services de domaine gardent leur signal _changed privé et exposent une méthode publique notifyChanged() ; PartieRealtimeService l'appelle, ne manipule jamais un signal externe directement. Binds : tout service de domaine consommé par PartieRealtimeService. Prevents : un couplage où le service temps réel connaît la représentation interne (signal writable) de chaque service de domaine.
- (decision) Sécurité endpoint SSE : GET /parties/:id/events réutilise le contrôle d'appartenance existant (getViewable/getOwned, même convention que le reste de l'API) — pas de nouveau mécanisme de garde pour ce endpoint.
- (decision) Multiplicité des connexions : une connexion SSE par instance de composant routé (ouverte au montage, fermée à la destruction via DestroyRef), pas de déduplication/partage entre composants ou onglets simultanés sur la même Partie. Accepté comme risque de simplicité, cohérent avec le Non-Goal PRD 'aucune préoccupation de montée en charge horizontale'.
- (decision) Résolution PRD Open Question 1 (FR-11 canal invitations) : le service de bus interne est généralisé à une clé de topic opaque (ex. 'partie:{id}', 'user:{id}') plutôt que verrouillé sur 'Partie'. Renommage : PartieEventsService/PartieRealtimeService deviennent RealtimeEventsService (backend)/RealtimeService (frontend). Binds : tout consommateur du bus (FR-1 à FR-14). Prevents : un deuxième service parallèle dupliquant la logique de connexion/reconnexion SSE pour un seul cas d'usage (invitations).
