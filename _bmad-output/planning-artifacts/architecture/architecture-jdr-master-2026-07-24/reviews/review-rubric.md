# Rubric Review — Palier 8 Architecture Spine (Refonte Ryuutama)

Reviewed: `_bmad-output/planning-artifacts/architecture/architecture-jdr-master-2026-07-24/ARCHITECTURE-SPINE.md`
Compared against: P7 (SSE), P5 (Homme Dragon), P6 (dette technique) spines; PRD `prd-jdr-master-2026-07-24`; `.memlog.md`; and the actual repo (`apps/api/prisma/schema.prisma`, `apps/api/src/game-systems/game-system.service.ts`, `packages/game-rules/src/ryuutama/{types,validate,pdf-field-map}.ts`, `apps/web/src/app/features/characters/character-wizard/**`, `apps/web/src/app/features/characters/character-sheet/character-sheet.ts`, `apps/web/src/app/features/parties/roster-row.util.ts`).

## Overall verdict

**Conditional pass — one high-severity gap, one real Deferred/Structural-Seed contradiction, two moderate gaps.** The spine's core reasoning (catalog pattern extension, JSON-vs-relational arbitration, module boundaries) is sound and correctly ratifies the brownfield code it does cite. But AD-2 (weapon restructure) does not account for **all** real consumers of the field it renames — it verifiably misses the PDF export mapping and the character-sheet display, both of which read `weaponCategoryId` directly today and will silently degrade (empty/warn, not a compile error) if not touched. This is exactly the kind of divergence-point-for-the-level-below the spine exists to catch, and it isn't caught for two of at least four real consumers.

## Findings, most severe first

### 1. [HIGH] AD-2's weapon rename misses two live consumers of `weaponCategoryId`: PDF export and character-sheet display
- **Where:** ARCHITECTURE-SPINE.md AD-2 (lines 55–59) and Structural Seed source tree (lines 191–201).
- **Claim:** "`RyuutamaSheetData.weaponCategoryId` is replaced by `weaponId: string`... The category ... is resolved at read time." The Structural Seed lists only `validate.ts`, `types.ts`, a new `weapon-resolve.ts`, and `weapon-step.ts` as touched.
- **Verified against repo:** `packages/game-rules/src/ryuutama/pdf-field-map.ts:176` calls `weaponPdfOption(data.weaponCategoryId)` to fill the "Arme Fav" field of the exported character PDF — a field that ceases to exist once AD-2 lands, per the spine's own text ("replaced by weaponId"). Likewise `apps/web/src/app/features/characters/character-sheet/character-sheet.ts:157` reads `this.sheetData()['weaponCategoryId']` directly to resolve the weapon-category content entry for the read-only sheet display. Neither file is mentioned anywhere in the spine (Rule text, Structural Seed, Consistency Conventions, or the `sources:` brownfield-read list in the frontmatter — which cites `validate.ts`/`types.ts`/`weapon-step.ts` but not `pdf-field-map.ts` or `character-sheet.ts`).
- **Failure scenario:** Two implementers both follow AD-2 literally. One additionally patches `pdf-field-map.ts`/`character-sheet.ts` because they happened to grep for `weaponCategoryId`; the other does exactly what the spine's Structural Seed enumerates and stops there. The second implementation compiles and passes the spine's stated tests (`validate.spec.ts`), but the exported PDF silently renders a blank "Arme Fav" field (the existing `weaponPdfOption` fallback swallows the failure with a `console.warn`, not an exception) and the character-sheet weapon panel silently shows nothing — a regression on an already-tested, in-production feature (`ryuutama-pdf.service.spec.ts` exists today) that no test in the spine's plan would catch.
- **Also implicated, not separately scored:** `game-system.service.ts#getSchema()` hardcodes `weaponCategoryId: { type: 'string' }` in `sheetSchema` and `{ key: 'weaponCategoryId', label: 'Arme favorite' }` in `creationSteps`; `character-wizard.ts` hardcodes `weaponCategoryId` in `SUPPORTED_STEP_KEYS`, `FIELD_TO_STEP_KEY`, and the `canGoNext` switch. AD-2/AD-9 never say whether the step key itself is renamed. If it's renamed without updating `FIELD_TO_STEP_KEY`, a server-side validation error on the new field silently reopens the wrong wizard step (falls back to `errors[0].field` as the step key, `findIndex` returns -1, wizard resets to step 0) instead of the weapon step.

### 2. [HIGH] AD-5's `@@unique([partieId, characterId])` is written into the Structural Seed as committed schema, while the same fact is simultaneously listed under Deferred as unconfirmed
- **Where:** ARCHITECTURE-SPINE.md AD-5 (lines 73–77), Structural Seed Prisma block (lines 144–157, `@@unique([partieId, characterId])`), Deferred table (line 225).
- **Issue:** The rubric asks whether "nothing under Deferred could let two units diverge" — i.e., deferred items must be genuinely non-load-bearing. Here the opposite happens: the Structural Seed (the artifact a dev-story would copy verbatim to write the migration) already bakes in the one-role-per-character constraint as a real `@@unique` index, complete with an inline comment "un personnage ne porte qu'un rôle à la fois (à confirmer, cf. Deferred)". But the Deferred table describes it as an open, unconfirmed "fast-path decision... to confirm with the user before implementation." A constraint that's already in the concrete schema block is load-bearing the moment a story implements this spine literally — reversing it later is a real migration (drop a unique index, and reconcile any int-implementation code that assumed at-most-one-role-per-character), not a free amendment. This is precisely the "disguised open fork" the checklist warns about: it reads as decided in one place and open in another, and whichever a given implementer notices first determines which behavior ships.
- **Failure scenario:** Story A implements the schema as literally written (constraint present, one role max). Story B (or the same developer reading only the Deferred table) treats it as still-open and defers writing the constraint, intending to "confirm with the user first" — producing a Character table with no such constraint. Both are individually defensible readings of this single document.

### 3. [MODERATE] Inherited Invariants table drops P1-AD-4 (`import type` for `@master-jdr/shared`) despite this spine introducing new cross-boundary types
- **Where:** ARCHITECTURE-SPINE.md Inherited Invariants (lines 37–45) — omits P1-AD-4, unlike the Palier 5 spine's equivalent table (which explicitly inherited it for the same reason: a new module/DTO crossing the api/shared boundary).
- **Verified against repo:** `apps/api/src/game-systems/game-system.service.ts` already follows the convention (`import type { GameSystemDto, GameSystemSchemaDto, GameSystemContentDto } from '@master-jdr/shared';`). Palier 8 introduces a new controller (`CharacterRolesController`), a new relational entity (`CharacterGroupRole`) that will need a DTO, and extends `RosterRow`/`CharacterDto`-adjacent shapes for `assignedRoleLabel` — all of which cross the same boundary. Silently omitting this inherited rule from the table doesn't break anything by itself (the convention is still real and likely to be followed out of habit), but it is exactly the kind of dimension-this-altitude-owns that the checklist says should be explicit, not implicitly assumed.

### 4. [LOW] FR-12's cardinality guarantee ("exactly 4 group roles, never more, never less") has no enforcement point named anywhere in the spine
- **Where:** PRD FR-12 Consequences ("Le catalogue de rôles contient exactement 4 entrées"); AD-1 only says the catalog is seeded like the others, with no validation step analogous to `validate()`'s referential checks.
- **Note:** This is defensible as "pure content, no architectural decision needed" (the spine explicitly treats classes/count-type FRs this way elsewhere, e.g. FR-4), so it is not scored as a full finding — but unlike FR-4 (classes), FR-12's constraint is phrased as a hard invariant ("jamais plus de 4, jamais moins") rather than a content-completeness goal, which makes it slightly more architecture-shaped than the spine credits. Worth a one-line acknowledgment in Deferred or Capability Map rather than silence.

## Rubric item-by-item

- **Fixes real divergence points, misses none:** Not satisfied — see Finding 1 (misses `pdf-field-map.ts`, `character-sheet.ts`, and the `getSchema()`/`SUPPORTED_STEP_KEYS`/`FIELD_TO_STEP_KEY` hardcoded-key chain).
- **Every AD's Rule is enforceable and prevents its divergence:** AD-1, AD-3, AD-4, AD-6, AD-7, AD-8, AD-9, AD-10 are enforceable and match the brownfield code read. AD-2 is enforceable in isolation but incomplete (Finding 1). AD-5 is enforceable but internally contradicted by its own Deferred entry (Finding 2).
- **Nothing under Deferred is a disguised open fork:** Fails once, at AD-5/Deferred (Finding 2). All other Deferred entries (reassignment/transfer, spell mechanic, plugin registry, `ContentEntry.scope` homebrew, multi-list equipment UI) are genuinely inert — none of them is pre-committed to code elsewhere in the spine.
- **Named tech is verified-current:** Pass. Confirmed against `apps/api/package.json` / `apps/web/package.json`: `@nestjs/common`/`@nestjs/core` `^11.1.28` (matches the P7 spine's "monter vers >=11.1.28" advice, already applied), `@prisma/client`/`prisma` `^7.8.0`, `@angular/core` `^22.0.0`. The Stack section correctly declares "no new dependency" and that holds.
- **Ratifies rather than contradicts the brownfield codebase:** Mostly yes for AD-1/AD-4/AD-6/AD-7/AD-8/AD-9/AD-10, verified directly against `game-system.service.ts` (`CONTENT_TYPES` shape, `seedRyuutama()`, `getSchema()`), `roster-row.util.ts` (`RosterRow`, `hasPendingLevelUp`, the three-branch `buildRosterRows` structure), and `schema.prisma` (`GlobalRole` enum, `Character`/`Partie` shapes — `CharacterGroupRole` fits cleanly, no naming collision beyond the `GlobalRole` one already flagged by the spine). AD-2 does not ratify the codebase fully (Finding 1).
- **Inherited invariants not weakened/contradicted:** P1-AD-1/2/3/5, P5-AD-4, P6-AD-1, P7-AD-4 are all correctly carried forward and not weakened. P1-AD-4 is silently dropped from the table (Finding 3) though not contradicted in practice.
- **Every dimension at this altitude is decided/deferred/open:** Mostly yes. The "no deployment changes, still carried by Palier 7" claim is reasonable and verified — no new env vars, no new external service, and the only operational wrinkle (adding 4 new required JSON files to `CONTENT_TYPES` means the API cannot boot until they exist and parse, per `seedRyuutama()`'s throw-on-missing-file behavior) is pre-existing behavior inherited from the P5 pattern, not a new risk this spine introduces — not worth scoring as a gap. RosterRow's three-branch structure (MJ / no-character / has-character) leaves it genuinely ambiguous which branch(es) populate `assignedRoleLabel` (can an MJ-owned `Character` hold a group role? — structurally possible per `schema.prisma`/`character.service.ts`'s `isMj` logic, since a `Character.userId` can equal `partie.mjId`), which AD-7 does not address; this is a minor gap adjacent to Finding 1's class of issue but lower-impact (cosmetic badge placement, not data-model breakage), so it is folded into this observation rather than scored separately.
