# Adversarial Divergence Review — jdr-master Palier 3 Architecture Spine

## Overall verdict

The spine is strong on Character-level concurrency for the two *named* xp writers but has five real gaps where two builders, each following the letter of an AD, produce incompatible or unsafe systems: an unlocked xp-write path, an unfenced generic-patch endpoint that can bypass the level-up wizard's own guarantees, an undefined trust boundary on who sets `addedBy`, a missing cross-Partie ownership check on distribution entries, and an ambiguous snapshot-creation contract for generic MJ edits. None of these are exotic edge cases — all five are the first thing an implementer hits while writing the obvious happy path.

## Findings

- **critical** AD-1 names exactly two `Character.xp` writers — `XpDistributionsService` and `CharacterService.setXp` — but the sequence diagram (lines 276–301) shows `XpDistributionsService` actually delegating the write to a *third*, unnamed method, `CharacterService.applyXpDelta`. AD-9's optimistic-lock bind list (line 137: "montée de niveau, édition MJ (xp et sheet-field), ajout d'objet par le joueur") does **not** include "application d'une distribution XP." A story-writer building the distribution-apply path can therefore correctly read the spine as saying `applyXpDelta` is exempt from the `updateMany({ where: { id, updatedAt } })` pattern, and implement it as a plain `prisma.character.update({ data: { xp: { increment: amount } } })` with no lock — while the MJ-direct-edit story-writer implements `setXp` exactly per AD-9, with the lock. Individually both are AD-compliant. Under concurrency: MJ opens the character, reads `xp=100`, computes a manual absolute target and calls `PATCH /xp { value: 250 }`; meanwhile a distribution applies `+50` via atomic increment, landing at `xp=150` and bumping `updatedAt`. MJ's optimistic-lock `updateMany` now correctly 409s — that part self-heals. But the more dangerous inverse case is real: if a *different* team member builds `applyXpDelta` as "read current xp, then `updateMany` with the `updatedAt` captured at read time, `data: { xp: currentXp + amount }`" (a legitimate, AD-9-consistent-looking implementation once someone assumes AD-9's "toute nouvelle mutation de `Character`" prose at line 137 governs it too), two concurrent distribution entries in the same `createDistribution` loop (or a distribution racing an MJ edit) will spuriously 409 each other, or — if the retry-on-conflict logic is skipped by whichever builder didn't think locking applied to their path — silently lose an XP grant. The spine gives no single answer to "does `applyXpDelta` take the optimistic lock, and is it atomic-increment or read-then-write." *Fix:* Add `applyXpDelta` explicitly to AD-9's bind list, and add one sentence to AD-1 mandating that `applyXpDelta` MUST use atomic `prisma.character.update({ data: { xp: { increment } } })` (no optimistic-lock read/compare needed because it's commutative), while `setXp` MUST use the `updateMany`+`updatedAt` absolute-overwrite pattern — and state explicitly that these two writers use *different* concurrency strategies by design, so no builder "reconciles" them into the same shape.

- **critical** AD-6 makes `PATCH /characters/:id/sheet-field` a generic `{path, value}` writer into `sheetData` (line 101), gated only by `validate('mj')` — which AD-7 explicitly guarantees "ne rejette jamais" (line 127, always returns `valid: true`). AD-2 stores level-up gains at `sheetData.levelUps[]` (lines 58–66), whose integrity (sum PV+PE=3, attribute cap=12, capability matches the level table) is enforced only inside the level-up wizard's controller logic (AD-6 line 97), never inside `validate()`. Nothing in AD-6 restricts which `sheetData` paths `sheet-field` may touch, and AD-6's own "Prevents" clause (line 96) only calls out the risk for `xp` specifically ("un endpoint générique unique... qui pourrait inclure `xp` en silence"), not `levelUps`. A story-writer implementing the generic patch endpoint per the letter of AD-6 has no textual reason to deny `path: "levelUps"` or `path: "levelUps[2].capability"` — it's just another `sheetData` path, and `validate('mj')` will pass it through with at most a warning per AD-7. This lets an MJ (via the same endpoint everyone already agrees is "MJ uniquement") directly inject a level-up entry with `pvAllocated: 5, peAllocated: 5` or an arbitrary `capability` unrelated to the character's actual level, silently corrupting `computeDerived`'s output (AD-2) and producing a `CharacterSnapshot` history that no longer matches what the level-up wizard would ever have allowed — with no separate AD to catch it, since AD-6's protection was scoped only to `xp`. *Fix:* Add an explicit AD-6 rule: `sheet-field` MUST reject (400, not silent-accept) any `path` whose root segment is `levelUps` or `xp` — those two subtrees are reserved exclusively for `POST /level-up` and `PATCH /xp` respectively. State the denylist as binding, not advisory (unlike the `validate('mj')` warnings).

- **high** AD-3 defines `InventoryItem { name, weight, addedBy: 'player'|'mj' }` but never states which layer sets `addedBy` or what happens if a client supplies it. The player-facing route `POST /characters/:id/inventory-items { name, weight }` (line 113) omits `addedBy` from its documented body, which *implies* server-side derivation for that endpoint — but never says so, and never says the server must strip/ignore an `addedBy` field if the client sends one anyway (a common NestJS DTO gap when `forbidNonWhitelisted` isn't specified, and it isn't specified anywhere in this spine). Meanwhile MJ-side inventory edits have no dedicated endpoint at all — they go through the generic `PATCH /sheet-field { path: "equipment.individual", value: unknown }` (AD-6), where `value` is client-constructed JSON with no schema check beyond non-blocking `validate('mj')`. So the MJ's frontend is the sole author of `addedBy` for every MJ-side inventory write, with zero server enforcement, while the player path's enforcement is only implicit. Two builders diverge concretely: builder A writes the player-inventory `CreateInventoryItemDto` with `@Allow()`-style pass-through (or no explicit whitelist), so a player who sends `{ name, weight: 0, addedBy: 'mj' }` in the POST body gets it persisted verbatim — spoofing an item as GM-issued (relevant if any future UI, PDF export, or encumbrance/weight-trust rule treats `addedBy: 'mj'` items specially). Builder B strips it correctly. Both "obey" AD-3/AD-6 to the letter because neither AD says who is authoritative for the field. *Fix:* Add to AD-3: "`addedBy` is never read from client input on any path; the player endpoint (`POST /characters/:id/inventory-items`) always writes `addedBy: 'player'`, and any `equipment.individual` mutation performed via `sheet-field` (MJ-only route) has `addedBy` forced to `'mj'` server-side regardless of what `value` contains" — with an explicit note that DTOs for the player route must reject an `addedBy` field in the request body (400), not silently drop it.

- **medium-high** AD-8 defines access control (who may call an endpoint) but not per-entity referential validation. `POST /parties/:id/xp-distributions { entries, ... }` (line 110) is gated by `parties.getOwned(partieId, mjId)` — proving the caller MJs *that* Partie — but nothing in AD-5, AD-6, or AD-8 requires `XpDistributionsService` to verify that each `entries[].characterId` actually belongs to `partieId` before writing an `XpDistributionEntry` and incrementing that character's `xp` via `applyXpDelta`. A story-writer who reads AD-8 literally ("actions MJ-only → `parties.getOwned`") may reasonably conclude the partie-level ownership check is the *complete* authorization story and skip a per-entry `character.partieId === partieId` check, since the Prisma schema (`XpDistributionEntry.characterId` at line 249) has no partie-scoped constraint either — it's a bare FK to `Character`, not a composite/scoped relation. A second builder, more defensive, adds the per-entry check. Concretely: an MJ of Partie A submits a distribution whose `entries` array includes a `characterId` from Partie B (typo, stale client state, or a client bug reusing a cached character list) — the unguarded implementation silently grants XP to a character outside the MJ's own campaign and records a permanent `XpDistributionEntry` for it, with no error, no audit flag, and no way to detect the drift from the history UI later since `GET /parties/:id/xp-distributions` (line 111) would show an entry whose character never appears in that Partie's roster. *Fix:* Add to AD-8 (or as an AD-5 rule on `XpDistribution`): "`XpDistributionsService.createDistribution` MUST validate `character.partieId === partieId` for every entry before any write; a mismatched entry rejects the whole request (400), not a partial apply."

- **medium** AD-6 states explicitly that a direct MJ xp edit "crée immédiatement un `CharacterSnapshot(trigger: 'MJ_EDIT')`" (line 97), but is silent on whether `PATCH /characters/:id/sheet-field` — the *other* MJ-edit mechanism defined in the same AD — also creates an `MJ_EDIT` snapshot. The `SnapshotTrigger` enum (line 219) and the `CharacterSnapshotDto` (lines 176–180) are generic enough that `'MJ_EDIT'` reads as "any MJ edit," not "MJ xp edit specifically," and `GET /characters/:id/history` (line 120) is presented to users as a general edit history, not an xp-only log. A story-writer building `PATCH /xp` wires snapshot creation into that one controller method per the literal AD-6 sentence; a story-writer building `PATCH /sheet-field` — reading the same AD-6 paragraph, which never mentions sheet-field snapshots — has no textual instruction either way, and can plausibly go either direction: (a) skip snapshot creation entirely (history silently misses all MJ sheet-field edits, e.g. MJ manually fixing an attribute or capability), or (b) add a snapshot on every sheet-field call (potentially firing on trivial edits, or firing twice if a single MJ action issues multiple sequential `sheet-field` PATCHes, cluttering history with noise `computeDerived` never intended to be snapshotted at that granularity). Either divergence produces a `history-tab` (line 163) that behaves differently depending on which builder wrote which endpoint, with no spine text to arbitrate. *Fix:* Add one explicit AD-6 sentence: "`PATCH /sheet-field` [creates / does not create] an `MJ_EDIT` snapshot on every successful call" — pick one, and if snapshots are desired, specify whether multiple patches within one MJ session should be coalesced or each produce its own row.
