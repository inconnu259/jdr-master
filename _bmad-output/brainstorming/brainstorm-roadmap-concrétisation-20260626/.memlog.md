# Session Memlog — Roadmap jdr-master

## Idées & insights — Côté MJ

- insight: Le MJ utilise Amsel Suite (amsel-suite.com) pour la préparation et les notes en live — offline, MJ-only, très puissant
- insight: jdr-master NE REMPLACE PAS Amsel pour la préparation MJ — il est la COUCHE DE PARTAGE entre MJ et joueurs
- insight: Problème réel = Amsel offline → pas de partage → joueurs se rappellent mal entre sessions → démarrage lent
- insight: Ce que jdr-master doit faire côté MJ = bridge Amsel ↔ joueurs : recaps partageables, XP, planning, évolution fiches
- decision: MVP MJ-side = léger : nom scénario, date jouée, résumé rapide, grandes lignes partageables
- idea: Visibilité granulaire des infos : certaines infos visibles par tous les joueurs, d'autres par sous-groupe, d'autres par 1 seul joueur (secret individuel)
- idea: Message secret en live = envoyer une info à un joueur spécifique pendant ou hors session (ex: "le PNJ te glisse à l'oreille...")
- idea: Entre sessions : MJ distribue XP, met à jour fiches, crée la prochaine session, relance les joueurs pour planning
- idea: Widget "résumé de campagne" visuel (PNJ rencontrés, événements marquants, timeline) → pour une version future
- idea: Import fichiers Amsel (JSON) → extraire infos cohérentes (PNJ, lieux, événements) vers jdr-master → long terme
- decision: "Scénario" MVP = session record : titre, date jouée, recap MJ (privé), recap joueurs (partagé), XP distribué, items importants, décisions clés
- decision: Session record = hybride : blocs structurés (items, décisions) + texte libre autour → les deux coexistent
- idea: Blocs structurés permettent des liens actifs : item trouvé → ajout direct à la fiche du joueur concerné
- idea: Notes joueurs partageables : chaque joueur peut prendre des notes sur une session, visibilité = participants+MJ ou MJ seul (choix du joueur)
- insight: Notes joueurs = données précieuses pour le MJ, et crée de l'engagement côté joueurs
- insight: Markdown serait une bonne base pour le texte libre (rendu riche, saisie simple) mais les blocs structurés restent des entités séparées en BDD

## Idées & insights — Calendrier

- insight: Problème réel = "vous êtes dispo quand ?" → galère de trouver des dates communes → sondage manuel inefficace
- insight: Inversion intelligente : au lieu de "quand êtes-vous dispo ?", chacun déclare ses INDISPOS → le système calcule l'intersection = les créneaux possibles automatiquement
- decision: 3 types d'indisponibilités : récurrent (ex: jamais le mercredi soir), ponctuel (ex: du 15 au 22 juillet), contrainte positive (ex: seulement le weekend)
- decision: Chaque indispo a une durée/expiration (ex: récurrent pendant 6 mois) pour éviter les données périmées
- idea: Flow calendrier = (1) chacun déclare ses indispos → (2) système calcule créneaux possibles automatiquement → (3) MJ propose dates parmi les créneaux libres → (4) vote optionnel si ambiguïté
- insight: C'est différent de Doodle : Doodle = MJ propose dates → vote. jdr-master = contraintes déclarées → système trouve les dates → vote si besoin
- question: Le MJ peut-il voir "les 5 prochaines dates où tout le monde est dispo" directement, sans passer par un vote ?

## Idées & insights — Architecture plugin

- idea: Plugin = interface commune (createCharacter, renderSheet, exportPDF, validate, computeDerived) mais chaque système implémente la sienne
- idea: Hiérarchie possible entre systèmes : module "D&D 5e (SRD)" parent, Draconis enfant qui hérite et surcharge
- idea: Pour comparer les systèmes et trouver les points communs, faire un relevé des spécificités par système (Draconis, Ryuutama, Conte de Minuit) avant de finaliser l'interface
- idea: Création de perso = deux modes selon complexité du système : UI step-by-step (Draconis complexe) ou formulaire simple (Ryuutama)
- idea: Référence créateur de perso : CorahnRin (Pierstoval) pour Esteren — workflow livre-like, adaptatif selon les choix
- insight: Un même plugin peut décrire COMMENT créer (steps) mais laisser le FRONT choisir comment le rendre (stepper vs formulaire)
- decision: Unifier step-by-step et formulaire = le plugin déclare des "steps" typées, le front choisit le rendu (stepper ou formulaire selon nbr d'étapes)
- insight: Esteren = 16 étapes, Draconis similaire, steps conditionnelles (si magie → étape sorts, si classe X → compétences Y)
- insight: Conte de Minuit = système libre, champs texte (race: [TEXTE], compétence: [TEXTE]) — le joueur invente, le MJ valide ou rejette avec contre-proposition
- idea: Workflow validation free-form : MJ approve/reject chaque champ libre + peut proposer une contre-proposition
- question: Peut-on unifier step-by-step et formulaire en un seul mécanisme de rendu, ou sont-ils vraiment deux cas séparés ?
- insight: Problème MJ override : si MJ modifie une stat, la fiche peut devenir "invalide" selon les règles joueur → bloquer le joueur injustement
- insight: Problème XP : MJ donne une compétence "gratuite" hors règles → le système ne sait plus calculer correctement l'XP restant → joueur bloqué injustement
- idea: Les "dons MJ" = des entrées trackées séparément (grantedItems[]) qui ne comptent pas dans le budget XP — le moteur les exclut du calcul
- idea: Mode "MJ valide" = MJ coche "je valide cette fiche" → joueur peut modifier librement MAIS toute modif passe en "pending MJ approval" avant d'être appliquée
- insight: Mode "MJ valide" est le mode dégradé ultime : peu importe les règles, le MJ a toujours le dernier mot
- decision: Architecture validation en 3 niveaux : (1) strict joueur, (2) MJ override ponctuel (dons trackés), (3) mode MJ-valide (approbation manuelle totale)
- question: Qui est propriétaire de la validité de la fiche ? Le système ou le MJ ? Proposition : "état MJ-override" qui suspend la validation strict jusqu'à prochaine action joueur

## MoSCoW — Résultat final

### MUST
- Comptes + auth (inscription sur invitation)
- Créer une partie (campagne / one-shot)
- Inviter des joueurs (in-app + lien)
- Architecture plugin GameSystem dès le départ
- Seed JSON automatique pour peupler Draconis
- Création de perso guidée (steps typées, Draconis)
- Validation fiche 3 niveaux (strict joueur / dons MJ trackés / mode MJ-valide)
- Évolution XP selon les règles
- Export PDF de la fiche
- Session record hybride (titre, recap MJ privé, recap joueurs partagé, XP, items structurés, décisions clés)
- Calendrier : indispos déclarées (récurrent + ponctuel) + calcul automatique + vote sur dates
- Bascule mode MJ ↔ Joueur

### SHOULD
- Notes joueurs partageables (visible joueurs ou MJ seul, choix du joueur)
- Workflow validation champs libres Conte de Minuit (MJ approve/reject + contre-proposition)
- Visibilité granulaire infos session (tous / sous-groupe / 1 joueur)
- Lien item session → fiche personnage (ajout direct)
- Calendrier contrainte positive ("seulement le weekend")
- Notifications email (SMTP) — SHOULD pour scope-1, BLOQUANT pour passage scope-2

### COULD
- Message secret MJ → joueur pendant session
- 2e système de jeu (Ryuutama ou Conte de Minuit)
- Widget résumé visuel de campagne (PNJ, timeline, events)
- Import fichiers Amsel JSON

### WON'T (for now)
- Carte interactive
- Éditeur de système complet sans coder
- Connexion Amsel live
- Modération / rôles avancés plateforme publique
- Back-office CMS contenu propriétaire

## Roadmap finale — ordre des paliers

- decision: Ordre roadmap = P1 (fondations, DONE) → P2 (calendrier) → P3 (moteur plugin + Ryuutama) → P4 (évolution & édition) → P5 (sessions & partage) → P6 (notifications + scope-2) → P7 (2e système)
- decision: Calendrier monté en P2 — valeur immédiate pour le groupe sans attendre les fiches
- decision: Ordre systèmes de jeu : Ryuutama (simple, valide archi plugin) → Conte de Minuit (teste champs libres) → Draconis (le plus complexe, en dernier quand archi prouvée)
- insight: Ryuutama first = stratégie risque minimal : si l'archi plugin est fausse, on le découvre sur le système le plus simple

## Decisions finalisées (réponses clarification)

- decision: Multi-système strategy = Option B (architecture plugin dès le départ, pour 2 systèmes rapidement)
- decision: Calendrier = inclure INDISPONIBILITÉS (#2) + VOTE pour dates (#3) dans MVP
- decision: Seed de données = reporter CMS, passer PDFs pour extraction directe en BDD (Angel)
