CharacterService n'a AUCUNE méthode update() — le chemin d'édition MJ (FR-14) et toutes les mutations de ce palier sont à créer de zéro. Pas de guard NestJS dédié au rôle — le pattern existant est un appel inline à `parties.getOwned`/`getViewable` dans chaque service. Verrouillage optimiste déjà établi pour les mutations de portrait (`updateMany({where:{id, updatedAt}})`, 409 si `count===0`) — pattern réutilisable directement. `GameSystemPlugin` (`canSpendXp`/`applyXp`/`sheetSchema()`) n'existe QUE dans `docs/spec.md`, aucune interface TS réelle, aucun registre de plugin — Ryuutama est appelé en dur/direct depuis `character.service.ts`, cohérent avec le commentaire existant de `GameSystemService.getSchema()` ("pas encore de registre de plugin par système"). `validate(data, 'mj', catalog)` est un no-op câblé en dur retournant toujours valide sans exécuter aucune règle. `sheetData.equipment.individual` est aujourd'hui `string[]` (texte libre, sans poids) — FR-9 nécessite un changement de forme. `packages/shared/src/index.ts` est un fichier unique (pas de sous-dossiers) ; aucun type XP/niveau/inventaire/notes/historique n'existe encore. EmailTemplate est un union type à 3 valeurs, facilement extensible.
- (decision) XP : nouvelle colonne `Character.xp Int @default(0)`, source de vérité unique, jamais dans `sheetData`. Le niveau n'est JAMAIS stocké — toujours dérivé via une nouvelle fonction `levelForXp(xp)` (table de seuils PRD §4.2), cohérent avec l'invariant PRD "niveau toujours dérivé de l'XP". Empêche les deux features qui touchent l'XP (distribution MJ, édition MJ directe) de diverger sur où/comment le lire.
- (decision) Gains de montée de niveau (répartition PV/PE, capacité choisie) stockés dans `sheetData.levelUps[]` (nouveau tableau Ryuutama-spécifique), pas dans une colonne séparée — `computeDerived(data)` reste une fonction pure de `sheetData` seul, sans élargir sa signature (contrat déjà consommé par `validate`/`pdf-field-map`/tests). "Montée en attente" = `levelForXp(character.xp) > sheetData.levelUps.length + 1`.
- (decision) `sheetData.equipment.individual` passe de `string[]` à `InventoryItem[]` (`{name, weight, addedBy: 'player'|'mj'}`). Nécessite un script de migration one-off pour les personnages déjà créés (Palier 2 a déjà livré la création de personnage, donc des lignes réelles existent avec l'ancienne forme). `pdf-field-map.ts` doit être mis à jour pour lire `.name` au lieu de la chaîne brute.
- (decision) Pas de registre `GameSystemPlugin` introduit dans ce palier — les fonctions XP/niveau vivent directement dans `packages/game-rules/src/ryuutama/` (nouveau fichier `leveling.ts`), importées directement par `CharacterService`, comme `validate`/`computeDerived` le sont déjà aujourd'hui. Différé jusqu'à l'arrivée réelle d'un 2e système de jeu (généraliser une interface pour un seul implémenteur serait de la généricité spéculative).
- (decision) Notes, Instantanés (historique), Distributions d'XP : 3 nouveaux modèles Prisma dédiés (`CharacterNote`, `CharacterSnapshot`, `XpDistribution`/`XpDistributionEntry`) — pas de tableaux JSON sur `Character`. Cohérent avec la convention déjà en place pour toute donnée en liste (`AvailabilityDeclaration`, `Invitation`, `InviteLink` sont des lignes relationnelles, jamais des tableaux JSON sur le parent) ; nécessaire aussi pour l'agrégation "historique des distributions par Partie" demandée par l'UX §2, impossible à reconstruire proprement depuis des instantanés de personnage isolés.
- (decision) Édition MJ du champ XP structurellement distincte de l'édition MJ d'un champ `sheetData` quelconque — deux endpoints séparés (`PATCH /characters/:id/xp` vs `PATCH /characters/:id/sheet-field`), pas un endpoint générique "patch n'importe quel chemin JSON" qui pourrait inclure XP en silence. Encode directement l'invariant signalé comme "high" par la revue qualité du PRD (FR-14 ne doit jamais contourner silencieusement le flux guidé FR-5/6). Une édition MJ directe de l'XP crée son propre instantané ("modifié par le MJ") immédiatement ; l'application ultérieure de la montée de niveau par le joueur crée un instantané séparé ("montée de niveau") — deux événements réels, pas fusionnés.
- (decision) `validate(data, 'mj', catalog)` exécute désormais les mêmes règles que `'strict'` mais retourne toujours `valid: true` — `errors[]` devient un signal consultatif (avertissement non bloquant côté MJ), jamais un rejet. Remplace le no-op actuel sans faire du mode MJ un mode bloquant (cohérent avec spec.md §5 "indicative pour le MJ").
- (decision) Contrôle d'accès de tous les nouveaux endpoints : réutilisation de `parties.getOwned`/`getViewable` (appel inline dans le service), pas de nouvelle classe de guard NestJS — cohérent avec la convention existante, pas de deuxième mécanisme d'autorisation à maintenir en parallèle.
- (decision) Verrouillage optimiste réutilisé pour toute nouvelle mutation touchant `Character` (montée de niveau, édition MJ champ, édition MJ XP, ajout d'objet par le joueur) — même pattern que `updatePortrait` (`updateMany` sur `updatedAt`, 409 si `count===0`). Nécessaire car la surface de mutation concurrente sur `Character` est bien plus large qu'au Palier 2 (MJ et joueur peuvent éditer en même temps).
- (decision) Angular : `PartieDetailComponent` se décompose en un roster (RosterRail desktop / RosterStrip mobile MJ) chargé une seule fois, et un contenu d'onglets qui ne recharge pas les participants indépendamment — évite la dérive déjà latente (aujourd'hui `characters` est chargé séparément du reste) après qu'une distribution d'XP ou une montée de niveau change le niveau affiché d'un personnage.
