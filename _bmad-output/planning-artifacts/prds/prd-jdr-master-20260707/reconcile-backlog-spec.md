# Réconciliation — PRD Palier 3 vs `docs/backlog.md` / `docs/spec.md`

## Verdict

Le PRD couvre fonctionnellement les quatre items non livrés de `backlog.md` §Palier 3 (XP, historique, inventaire/notes, édition MJ) et ne contredit pas l'architecture plugin ni le modèle de données de `spec.md` sur le fond ; le seul point notable est une **divergence de terminologie/modèle autour de l'XP** (« jamais dépensé » dans le PRD vs `canSpendXp`/« dépense d'XP » dans `spec.md`/`backlog.md`) que le PRD ne mentionne ni ne réconcilie explicitly, plus deux écarts mineurs (garantie d'indication MJ non reprise, mécanisme de "versions" réduit à un journal en lecture seule).

## Gaps / points à vérifier

- **Contradiction terminologique sur le modèle d'XP** — `backlog.md` ligne 68 : *« Évolution par **XP** (`canSpendXp` / `applyXp`) selon les règles. »* et `spec.md` ligne 54 : *« **Faire évoluer son perso** : dépense d'**XP** selon les règles (montée de niveau / achats). »* — ces deux sources désignent un modèle où le joueur **dépense** de l'XP (nom de méthode `canSpendXp`, verbe « dépense »). Le PRD définit à l'inverse (§3 Glossaire, ligne 44) : *« XP (points d'expérience) — Compteur cumulatif sur le personnage, **jamais dépensé, jamais remis à zéro**. »*, répété en §4.2 (ligne 107) : *« L'XP d'un personnage ne se dépense jamais... »*. Le PRD ne cite nulle part `canSpendXp`/`applyXp` (recherche infructueuse dans `prd.md`) et ne explique pas comment son modèle "seuils cumulatifs, jamais dépensés" se mappe sur une interface `GameSystemPlugin` dont les noms de méthodes (`spec.md` lignes 111-112) impliquent une dépense. Fonctionnellement compatible (on peut implémenter des seuils avec `applyXp` appelé par palier franchi), mais le PRD aurait dû lever explicitement cette tension de vocabulaire/modèle héritée de la spec plutôt que de la passer sous silence — risque de confusion à l'implémentation (l'architecte pourrait chercher un mécanisme de "points à dépenser" qui n'existe pas dans ce PRD).
  - Localisation PRD : §3 Glossaire (ligne 44), §4.2 (ligne 107) — absence totale de `canSpendXp`/`applyXp`.

- **Garantie « avertissements, jamais de blocage » pour le mode MJ non reprise explicitement** — `spec.md` ligne 42-44 : *« la validation du moteur de règles est **bloquante pour le joueur**, mais **seulement indicative pour le MJ** (avertissements, jamais de blocage). »* Le PRD (FR-14, ligne 221) reprend bien le "jamais de blocage" (*« elle ne doit pas rejeter une valeur... »*) mais ne mentionne pas la notion d'**avertissement/indication** que `validate(data, 'mj', catalog)` est censée produire (ex. signaler au MJ qu'une valeur sort du catalogue, sans bloquer). Le PRD dit seulement que l'édition est permissive, sans préciser si le MJ voit un signal quelconque sur les valeurs hors catalogue.
  - Localisation PRD : §4.6 / FR-14 (lignes 213-224) — pas de mention d'avertissement visuel MJ.

- **« Historique / versions » du backlog réduit à un journal en lecture seule sans notion de version consultable/restaurable** — `backlog.md` ligne 69 dit *« **Historique / versions** de la fiche »*, un intitulé qui peut suggérer une gestion de versions (comparaison, retour arrière). Le PRD choisit explicitement un scope plus restreint : instantanés en lecture seule, sans revert (§4.5, Non-Goals ligne 230, Open Question déjà notée §6.2). Ce n'est pas une contradiction dure — le PRD assume et documente ce choix comme « à revoir si besoin » — mais c'est une réduction de portée par rapport à la lettre du backlog qui mérite d'être signalée comme un point de relecture avec le PM plutôt qu'un gap silencieux (le PRD le fait déjà bien via `[NOTE FOR PM]` ligne 249, donc ce point est **déjà correctement traité**, mentionné ici pour complétude).

## Points vérifiés sans écart

- Les quatre items non cochés du Palier 3 (XP, historique, inventaire/notes personnelles, édition MJ) sont chacun couverts par une section dédiée du PRD (§4.1-4.2, §4.5, §4.3-4.4, §4.6).
- L'export PDF est correctement traité comme hors scope (§0), cohérent avec `backlog.md` ligne 72 (`[x]` déjà livré).
- Le modèle de données du PRD (`Character.sheetData`/`derived`, inventaire, notes, historique) correspond exactement aux champs listés dans `spec.md` ligne 154-155 (*« gameSystemId, sheetData (JSONB), derived, inventaire/équipements, notes du joueur, versions/historique »*).
- L'architecture plugin existante (`GameSystemService`, `CharacterService`, séparation moteur/contenu, seed JSON gitignoré) est respectée et explicitement non redéfinie (§0), cohérent avec `spec.md` §5 et `backlog.md` Palier 2.
- Aucun contenu surprenant hors sujet : les règles Ryuutama détaillées (tables XP, capacités de niveau) sont explicitement qualifiées par le PRD lui-même comme « contenu spécifique au système », au même titre que les classes/types/armes du Palier 2 — cohérent avec la séparation moteur/contenu de `spec.md` §5.
